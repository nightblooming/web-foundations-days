### Course Reflection

The most challenging concept in the course was managing distributed state and concurrency during high-contention events, specifically preventing race conditions without tanking system throughput. Wrapping my head around the boundary between cache layers and transactional consistency—such as when to rely on atomic database row-level locks versus distributed Redis locks—initially felt overwhelming. I overcame this by building isolated, concurrent test harnesses using tools like Locust and Go routines. Seeing firsthand how optimistic concurrency checks failed under high volume versus how row-level updates held firm demystified transaction isolation levels and lock queues.

Based on peer and mentor feedback on my capstone, the primary area I would improve is edge-case failure handling in asynchronous fulfillment. While the core booking and payment flow performed reliably, the downstream reconciliation loop—specifically handling webhook drops and mid-transaction timeouts during payment settlement—relied too heavily on basic retries. I would introduce an explicit outbox pattern and an automated dead-letter queue recovery worker to ensure complete idempotency and eliminate any manual intervention during network splits.

Next, I plan to dive deeper into distributed streaming systems and event-driven architecture, specifically mastering Apache Kafka internals and partition strategies. I want to explore how high-throughput event logs handle stateful stream processing and out-of-order event resolution at scale, moving beyond simple pub/sub implementations to design genuinely resilient, event-sourced backends.
